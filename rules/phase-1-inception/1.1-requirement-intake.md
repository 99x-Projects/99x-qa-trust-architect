# Stage 1.1 — Requirement Intake

**Goal:** bring the work item into the canonical model, establish scope and tier.
**Agent:** `requirement-analyst`. **Output:** `1-inception/requirement.md`, `qa-state.md`.

## Inputs
- Work item ID (from `/qa-start`) — or AI-DLC unit (if `keyBy: unit`)
- Adapter: `getWorkItem`, `getLinkedItems` (parent epic/feature, child tasks, related bugs, PRs)
- Context slices: overview, glossary, features

## Steps
1. **Fetch** via adapter → map to `schemas/work-item.schema.json` using the adapter's
   `mapping.yaml`. Keep the raw description (HTML → Markdown) for reference.
2. **AI-DLC companion:** if the item maps to an AI-DLC unit/story, also load the mapped
   AI-DLC requirement and story artifacts (`integrations/aidlc/mapping.yaml`) and record
   them as sources (`source: aidlc:<path>`). Don't copy them — link and summarise.
3. **Split into requirement statements** `REQ-01..` — one testable behaviour per statement.
   Keep the original wording quoted.
4. **Existing AC:** extract any AC already on the work item as `AC-xx (draft, source: platform)`.
5. **Resolve feature scope** via `core/context-loader.md` §1 (may trigger lazy deepening).
6. **Route**: decide tier (`core/routing-rules.md`); write stages list into `qa-state.md`.
7. Create `ITEM_DIR` skeleton: `qa-state.md`, `audit.md`, `questions.md`, folders.

## Output sections (`templates/requirement.md`)
Summary · Source links · REQ statements · Existing AC · Feature scope (+ match reasons) ·
Linked items · Tier decision.

## Self-check
- [ ] Every sentence of the description is covered by a REQ or explicitly marked non-functional/context
- [ ] Feature scope has ≥ 1 feature or a question asks for it
- [ ] Tier recorded with reason
