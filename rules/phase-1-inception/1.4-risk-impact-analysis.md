# Stage 1.4 — Risk & Impact Analysis

**Goal:** decide where testing effort goes (risk-based testing) and what could break
(impact / regression surface).
**Agent:** `risk-gap-analyst`. **Output:** `1-inception/risk-assessment.md`.

## Context slices
features, rules, hotspots, integrations, existingTests, nfr, quirks

## Steps
1. **Identify risks** `R-01..` per AC/feature area across categories:
   functional, data integrity, security/privacy, performance, integration, usability/a11y,
   compatibility, operational (deploy/config/migration), regulatory.
2. **Score** each risk: Likelihood (1–5) × Impact (1–5) → 1–25.
   - Likelihood drivers: complexity, change size, hotspot history, new tech, unclear reqs
   - Impact drivers: user exposure, money/PII/compliance, blast radius, recoverability
   Rating: 1–6 low · 7–14 medium · 15–25 high.
3. **Impact / blast radius** (brownfield):
   - Changed or to-be-changed code areas (from PR/commits if available, else from feature map)
   - Callers, dependents, shared components, data consumers, integrations (one hop; two for comprehensive)
   - Optional: delegate to `impact-analyst` plugin if installed (record that it was used)
4. **Regression selection**: list existing tests (from `feature-test-map.yaml`) that cover
   impacted areas → candidate regression set; note areas with **no** existing coverage
   (feeds 1.5).
5. **Mitigation per risk**: test types/depth, specific AC/TC focus, monitoring (2.4), or
   accept (with reason).

## Self-check
- [ ] Every AC is covered by ≥ 1 risk entry or explicitly low-risk
- [ ] Every high risk has a mitigation
- [ ] Regression candidates listed (brownfield)
