# Stage 2.1 — Test Case Design

**Goal:** a traceable set of test cases that covers every AC and is proportionate to risk.
**Agent:** `test-designer`. **Output:** `2-design/test-cases/TC-xxx-<slug>.yaml`
(schema `schemas/test-case.schema.json`; templates `templates/test-case.gherkin.yaml`,
`templates/test-case.rule-table.yaml`) + `2-design/test-case-index.md`.

## Context slices
glossary, rules, entities, roles, journeys, nfr, environments, quirks

## Techniques (choose per AC; record `technique` on each TC)

| Technique | Use when |
|---|---|
| Equivalence partitioning | Input domains with classes of equivalent behaviour |
| Boundary value analysis | Any numeric/date/length limit (test min-1, min, max, max+1) |
| Decision table | Rule-table AC; combinations of conditions |
| State transition | Entity state machines (valid and **invalid** transitions) |
| Pairwise / combinatorial | Many independent parameters (browsers × roles × options) |
| Use-case / journey | End-to-end flows from `journeys/` |
| Error guessing | Known quirks, hotspots, past bugs for the feature |
| Permission matrix | Role × action for every role in scope |
| NFR checks | Performance thresholds, a11y checks, security abuse cases |

## Format per AC
- Gherkin AC → **Gherkin test case** (scenario/scenario outline with examples).
- Rule-table AC → **rule-table test case** (steps + data table).
Keep the same format the AC used unless the designer has a reason (record it).

## Steps
1. For each AC: pick techniques → derive cases. Risk rating drives depth:
   high = all techniques that apply; medium = EP + BVA + negative; low = happy + 1 negative.
2. Fill each TC: title, objective, preconditions, data, steps/scenario, expected results,
   priority (from risk), `level` suggestion (unit/api/ui/manual), `traces` (REQ, AC, BR, R, F),
   `basis` (confirmed/provisional).
3. **Reuse**: if an existing test (feature-test-map) already covers the case, create the TC
   with `existingCoverage: <path>` instead of a duplicate — needed for traceability.
4. Build `test-case-index.md`: table TC × AC × priority × level × basis; AC coverage matrix.
5. Avoid oracle problems: expected results must come from AC/confirmed rules — if only a
   provisional fact supports an expected result, tag it and add a question.

## On G3 approval → sync
Adapter `upsertTestCase` per TC (stores returned ID in `externalIds.<platform>`),
`linkItems(TC ↔ work item)`, and suite organisation per adapter rules.

## Self-check
- [ ] Every AC has ≥ 1 TC; every high-risk AC has negative + boundary TCs
- [ ] Every TC traces to ≥ 1 AC
- [ ] No duplicate TCs (same AC + same data class + same expected result)
- [ ] Expected results are specific and observable
