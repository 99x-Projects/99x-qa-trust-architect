# Stage 2.2 — Test Data & Environment Design

**Goal:** every test case can be executed — the data it needs exists in the right state, in the
right environment, with the right accounts and integrations — without real personal data and
without surprises on execution day.
**Agent:** `test-designer`. **Output:** `2-design/test-data.md` (template `templates/test-data.md`);
optional machine-readable data sets `2-design/data-sets/DS-xx.yaml` (template `templates/data-set.yaml`).
**Runs:** comprehensive tier; standard tier when **any** of: a TC needs an entity in a non-initial
state, more than one role, an integration, time-dependent behaviour, volume, or a feature flag.

## Context slices
entities, roles, environments, integrations, rules, nfr

## Inputs
- `2-design/test-cases/*.yaml` (preconditions, data rows, roles, levels)
- `entities-states.yaml`, `personas-roles.yaml`, `environments.yaml`, `integrations.yaml`
- `_project/qa-profile.yaml` → `testData` (seed scripts, factories/builders, fixtures, data APIs)
- `_project/quality-standards.md` (privacy and NFR targets), `1-inception/test-plan.md` §4

## Steps

### 1. Derive data requirements per TC
For each TC (and each Examples/data row) record:
| Dimension | Example |
|---|---|
| Entity + state | `ENT-leave-request` in `Submitted` (states from `entities-states.yaml`) |
| Attribute values | boundary values from the TC (20, 21 days) |
| Relationships | employee with a manager; manager with ≥ 1 direct report |
| Role / account | `ROLE-manager` |
| Time | **relative**, never hard-coded: "start = next working day", "created 31 days ago" |
| Volume | "≥ 500 requests in list" for paging/performance TCs |
| Uniqueness | needs a fresh record per run (e.g. "first request of the year") |
| External state | email inbox capture; payment sandbox approved/declined card |

### 2. Consolidate into data sets (`DS-01..`)
- Group requirements with the same shape; aim for the **fewest** sets that keep TCs independent.
- Mark each set **shared/read-only** (reference data, safe to reuse) or **exclusive** (TC mutates
  it → one copy per TC or per run). Destructive/state-changing TCs never share mutable data.
- Note the TCs that use each set (also write `dataSets` on each TC).

### 3. Choose the creation method (prefer top of the list)
| Method | Use when | Notes |
|---|---|---|
| Existing factory/builder/seed in the repo | Detected in `qa-profile.yaml` | Reuse; name the function/script |
| Application API | API exists for the entity/state | Deterministic, fast, uses business rules |
| Fixture file / import | Reference data, bulk volume | Versioned with the tests |
| Synthetic generator | Volume or variety | Seeded generator for repeatability |
| UI | No API/seed possible | Slow; only for small sets; becomes an automation blocker |
| Direct DB insert | Test env only, owner agreed | Bypasses rules — state why it is safe |
| Masked production copy | Realism needed and synthetic insufficient | **Requires named privacy approval**; masking spec mandatory |

### 4. Lifecycle
For each set: when it is created (pre-cycle / per suite / per TC), how it is reset or cleaned up,
interaction with the environment's `dataResetPolicy`, and collision risks (other teams, parallel
runs → use a unique prefix such as `QA-<workItemKey>-…`).

### 5. Privacy classification (mandatory)
Classify every field used: `none` · `personal` · `sensitive` (health, financial, children, …) ·
`secret`. Rules:
- Synthetic values only for `personal`/`sensitive`: names from a fake generator, emails on reserved
  domains (`example.com`, `example.org`, or the team's test domain), phone numbers from fictional
  ranges, addresses fake, IDs generated.
- Payment data: the provider's published **test card numbers** only.
- `secret` values (passwords, keys, tokens): **references only** (`env:NAME`), never values.
- Masked copies: list each masked field and the technique (substitute, shuffle, hash, null).

### 6. Accounts
Role × environment matrix with **references** from `environments.yaml` (never values). Missing account,
missing role on an environment, or MFA that blocks testing → `GAP-xx` (environment) and a question.

### 7. Environment needs
| Need | Decide |
|---|---|
| Environment | which one from `environments.yaml` and why; build/version expected |
| Feature flags | required state per TC; flag-guarded behaviour needs TCs for **both** states (add a question if 2.1 missed one) |
| Configuration | differences from production that affect TCs (limits, timeouts, locales) → env-parity risk |
| Integrations | per `integrations.yaml` entry: real sandbox / stub / mock / service virtualisation, and whether **failure modes** can be simulated (needed for failure-mode TCs) |
| Time control | can the clock be set/frozen (for date rules)? If not → workaround or GAP |
| Message capture | email/SMS/notification capture (test inbox, mail catcher) for notification TCs |
| Observability | access to logs/metrics in the test env (needed for 2.4 verification checks) |

### 8. Readiness
Table of every data set, account and environment need with status `available` / `to-create` /
`blocked`, owner and needed-by date. Anything not `available` becomes an **entry criterion** in the
test plan (§6) — 3.2a checks it before execution.

### 9. Gaps
New data/environment problems not already in `gap-analysis.md` → append `GAP-xx` (types `data`,
`environment`) with impact on TCs.

## Self-check
- [ ] Every TC (and data row) maps to a data set; every set lists its TCs
- [ ] No hard-coded dates; mutating TCs use exclusive data
- [ ] Every field classified; no real personal data; secrets only as references
- [ ] Every integration used has a stub/sandbox decision and failure-mode capability noted
- [ ] Every non-available item has an owner, date and entry criterion
