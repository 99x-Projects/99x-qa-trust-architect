# Stage 2.4 — Observability Design

**Goal:** decide how we will **know in production** that the change works — and notice quickly
when it doesn't — and make sure those signals are verified before release.
**Agent:** `risk-gap-analyst`. **Output:** `2-design/observability-plan.md`
(template `templates/observability-plan.md`).
**Runs:** comprehensive tier; standard tier when the change is user-facing or touches an integration.

## Context slices
integrations, nfr, features, hotspots

## Inputs
- `1-inception/risk-assessment.md` (high/medium risks), `acceptance-criteria.md`, journeys in scope
- `integrations.yaml` failure modes, `_project/quality-standards.md` NFR targets
- `_project/qa-profile.yaml` → `observability` stack (Application Insights, OpenTelemetry, Datadog,
  Prometheus/Grafana, ELK, Sentry, …)
- Impacted code (read-only Grep/Glob) for existing instrumentation

## Steps

### 1. Scope
Everything that needs a production answer: high and medium risks, the main success path of each
key AC ("did users complete it?"), every integration failure mode in scope, NFR targets
(latency, error rate, availability).

### 2. Inventory existing instrumentation
Grep the impacted code for logging and telemetry (e.g. `ILogger`, `logger.info`, `TelemetryClient.Track*`,
`Meter.Create*`, `ActivitySource`/OpenTelemetry spans, `Sentry.capture*`, `statsd`). Record what is
already emitted and the **naming conventions** in use (event names, metric prefixes, dimension names).
New signals must follow them.

### 3. Design signals — "how would we know in production that X broke?"
For each scoped item choose one or more:
| Type | Use for | Rules |
|---|---|---|
| Structured log event | Business events, rejections, failures with context | Fixed event name; fields: correlation id, entity id (opaque), role, outcome, reason code — **no PII, no free text from users** |
| Metric | Rates, counts, latency | **Low-cardinality** dimensions only (outcome, reason, region) — never user/entity ids as labels |
| Trace span | Calls across integrations | Span per outbound call with dependency name, outcome, duration |
| Business KPI | Outcome health | e.g. approval completion rate, abandonment at step 3 |
| Audit record | Compliance-relevant actions | Who/what/when, immutable |
Name each signal per the conventions found in step 2; give its purpose and the risk/AC it serves.

### 4. Detection — alerts and SLOs
- **Alert** per signal that indicates harm: condition written as a **query sketch in the stack's
  language** (KQL for Application Insights/Log Analytics, PromQL, Datadog, Elastic/Lucene), window,
  threshold with rationale (no baseline yet → conservative threshold + "tune after 2 weeks"), severity,
  route (team/channel/on-call), runbook link placeholder.
- **SLO** for each NFR target in scope: SLI definition (good events / valid events), objective, window,
  error-budget policy owner.
- Avoid alert noise: every alert must be actionable; informational signals go to dashboards.

### 5. Dashboards
One panel list for the feature: KPI, error rate, latency p95, integration health, top rejection reasons.

### 6. Synthetic checks
Key journeys (from `journeys/`) that get a production synthetic monitor: steps, frequency, locations,
success criteria. **Safe-path only** in production (read-only, or a designated test tenant/account);
never create real transactions.

### 7. Testability and instrumentation asks
What developers must add: missing events/metrics/spans from step 3, correlation-id propagation, health
and readiness endpoints (with dependency checks), structured error codes, feature-flag introspection.
List as **dev asks** `DA-xx` (shared numbering with 2.3); optionally created on the platform at G3
(tag `qa-observability`).

### 8. Verification before release (`OBS-xx` checks)
For each new or changed signal/alert, a check QA runs in a test environment during Phase 3:
"Trigger <action> → within <time> the <signal> appears in <tool> with fields <…> and **no PII**";
"Simulate <failure mode> → alert <name> fires". These are executed in 3.2a and recorded as runs with
`testRef: OBS-xx`; results feed the test summary report. Checks that need production access are marked
for 4.2 (observability validation after release).

### 9. Not observable
Risks with no reasonable production signal → listed with reason and the compensating control
(more pre-release testing, manual check after deploy). These are residual risks for G4.

### 10. Gaps
Missing stack access in test environments, missing instrumentation libraries, no alert routing →
`GAP-xx` (type `observability`).

## Self-check
- [ ] Every high risk has ≥ 1 production signal or a "not observable" entry with compensating control
- [ ] Signal names follow existing conventions; no PII in fields; metric dimensions low-cardinality
- [ ] Every alert has condition, window, threshold rationale, severity, route
- [ ] NFR targets in scope have SLOs
- [ ] Every new/changed signal has an OBS check
