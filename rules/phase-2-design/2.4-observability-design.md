# Stage 2.4 — Observability Design  *(MVP: draft quality)*

**Goal:** decide how we will **know in production** that the change works — and detect
when it doesn't.
**Agent:** `risk-gap-analyst`. **Output:** `2-design/observability-plan.md`.
**Runs:** comprehensive tier; standard tier if user-facing or touching an integration.

## Steps
1. For each high/medium risk and key AC, define **signals**:
   - Logs: event names, required fields (correlation ID, user role, entity ID — no PII)
   - Metrics: counters/histograms (e.g. `leave_request_submitted_total`, latency p95)
   - Traces: spans across integrations
   - Business KPIs: e.g. approval completion rate
2. **Alerts / SLOs:** threshold, window, severity, routing; link to NFR targets.
3. **Synthetic checks:** which journeys get a production synthetic (v2/v4 executes them).
4. **Testability hooks** to request from developers (health endpoints, feature-flag
   introspection, test-mode headers) — list as dev asks.
5. Use the detected observability stack (`qa-profile.yaml`) for concrete naming.

## Self-check
- [ ] Every high risk has ≥ 1 production signal or an explicit "not observable" reason
- [ ] No PII in proposed log fields
