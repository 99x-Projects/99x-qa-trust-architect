# Stage 2.3 — Automation Gap Identification

**Goal:** for every test case decide whether, where and how it should be automated — at the lowest
level that can observe the expected result — reuse what already exists, and turn the rest into a
concrete, prioritised automation backlog.
**Agent:** `automation-analyst`. **Output:** `2-design/automation-gap.md` (template
`templates/automation-gap.md`); updates `level` and `automation.*` on each TC.
**Runs:** standard and comprehensive tiers.

## Context slices
features, existingTests, appmap, integrations, nfr

## Inputs
- `2-design/test-cases/*.yaml`, `test-case-index.md`, `2-design/test-data.md` (if 2.2 ran)
- `1-inception/risk-assessment.md` (risk per TC via traces)
- `_project/qa-profile.yaml` (test frameworks, paths, CI and what it runs), `_project/feature-test-map.yaml`
- `_project/quality-standards.md` → test levels policy, automation target %
- The test code itself (read-only Grep/Glob)

## Steps

### 1. Decide the level (push down)
| The expected result depends on… | Level |
|---|---|
| A calculation / rule / validation inside one component | `unit` |
| Endpoint behaviour: validation, status codes, persistence, authorisation | `api` |
| The agreement between two services/apps (request/response shape) | `contract` |
| What the user sees and does across pages; UI-only logic; layout; a11y | `ui` |
| Human judgement (usability, look & feel), one-off checks, unclear oracle | `manual` |
| Discovery rather than confirmation | `exploratory` |
Choose the **lowest** level that can observe the expected result. A UI TC whose expected result is a
business rule should usually be split: rule at unit/API, plus one UI journey check. Record the split
as a suggestion (2.1 owns the TCs).

### 2. Match existing automation
Search the test code for each TC: TC id in names/categories, rule ids, route/endpoint, distinctive
values (boundary numbers, error message text), feature keywords; then `feature-test-map.yaml`.
Classify:
- `already-automated` — an existing test asserts the same expected result → `existingCoverage: <path>::<test>`
- **partial** — an existing test covers part (same flow, other data) → status `candidate`,
  `automation.extends: <path>::<test>` (cheaper than a new test)
- none
State the evidence (file + assertion) for every match; never claim coverage from a file name alone.

### 3. Score candidates (1–5 each, anchors below)
**Automation value = (F + R + S + D) − E**

| | 1 | 3 | 5 |
|---|---|---|---|
| **F** Frequency | run once | each release | every commit/PR (regression core) |
| **R** Risk | low risk area | medium | high risk / hotspot / money, PII, security |
| **S** Stability | UI/flow still changing | settling | stable contract/UI |
| **D** Determinism | depends on time/external/random, no control | partly controllable | fully controlled data and result |
| **E** Effort | trivial (< 1 h, framework ready) | ~1 day | multi-day or needs a framework gap fixed |

Recommendation: **≥ 12 automate now** (this item) · **8–11 backlog** · **< 8 keep manual** (reason).
`manual-only` always needs a reason (judgement, cost > value, cannot control, one-off).

### 4. Feasibility blockers
For each candidate, list blockers and the **dev ask** that removes them:
| Blocker | Dev ask |
|---|---|
| No stable selectors | add `data-testid` / accessible names on listed elements |
| Data can't be set up without UI | test-data API / builder (links to 2.2) |
| External dependency without stub | stub/sandbox or contract test |
| Time/random/async nondeterminism | injectable clock, seeded random, wait-for hooks |
| Auth/MFA in automation | test-auth bypass in non-prod, service accounts |

### 5. Framework gaps
Compare the levels needed against `qa-profile.yaml`: missing framework for a level (no API test
project, no UI framework), framework present but **not run in CI**, missing reporters (no JUnit/TRX →
results can't be imported in 3.4), missing builders. Each → `GAP-xx` (type `automation`) with impact.

### 6. Placement for every "automate now" / backlog item
Target **framework**, **path** following the repo's existing conventions, **test name containing the
TC id** (e.g. `TC-001_rejects_request_over_20_days`, or a category/tag `TC-001`) so 3.4 links results
automatically, **pipeline stage** (PR / nightly / release), tags (feature, risk).

### 7. Backlog
Group items by level and feature into backlog entries `AB-01..` with TCs, level, framework/path,
estimate (S ≤ ½ day · M ≤ 2 days · L > 2 days), blockers/dev asks, and done-when:
"test exists, named/tagged with its TC ids, runs in <pipeline>, passes, reports JUnit/TRX".
On G3 approval, **if the tester agrees**, create them on the platform (adapter `createWorkItem`,
tag `qa-automation`); dev asks may be created as separate items (tag `qa-testability`).

### 8. Update the TCs
Set on each TC: `level`, `automation.status` (`candidate` / `already-automated` / `manual-only` /
`exploratory`), `automation.value`, `automation.target` (framework, path, testName, stage),
`automation.extends`, `automation.blockers`, `existingCoverage`, `automation.reason` for manual-only.

### 9. Summary
Automation ratio for this item (automated + automate-now) / total vs the policy target; regression
contribution (which become regression tests); flakiness risks.

## Self-check
- [ ] Every TC has a level and automation status
- [ ] Every `already-automated` / `extends` claim has file + assertion evidence
- [ ] Every candidate has F/R/S/D/E scores; every `manual-only` a reason
- [ ] Every automate-now/backlog item has framework, path, TC-id naming, pipeline stage
- [ ] Framework gaps and dev asks listed
