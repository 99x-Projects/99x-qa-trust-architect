# Stage 3.2b — Exploratory & Focused Testing via Playwright MCP

**Goal:** find what scripted test cases miss — by exploring the running application in a real
browser, guided by the domain context, within a time-boxed charter, and leave behind evidence,
not impressions.
**Who:** `/qa-explore` (orchestrator) and the `exploratory-tester` agent.
**Browser:** the Playwright MCP server (`.mcp.json` → `playwright`, package `@playwright/mcp`).
It drives the page through its **accessibility snapshot** (no screenshots needed to act).
**Output:** `ITEM_DIR/3-execution/charters.md`, `3-execution/sessions/<SES-id>/{charter.md,
session-report.md, evidence/}`; defect drafts (3.3), questions, DCPs, TC and automation suggestions.

## 1. Session types

| Type | Built from | Typical length |
|---|---|---|
| **Focused** | Impact areas (1.4) + gaps (1.5) for this work item | 20–30 min |
| **Charter-based exploratory** | High risks (1.4), hotspots, journeys touching scope | 30–45 min |
| **Bug re-verification** | A `DEF-xxx` with platform state fixed/resolved | 5–15 min |
| **Smoke** | Key journeys of scope features after a deployment | 10 min |

## 2. Modes

| Mode | Who drives | Where it runs | Use when |
|---|---|---|---|
| `autonomous` | AI, inside the charter and time box | `exploratory-tester` agent (sub-agent) | Wide, low-risk exploration; the tester reviews the report afterwards |
| `guided` | Tester steers in chat ("now try it as a manager"), AI operates the browser | Main session (`/qa-explore`) | Focused investigation, reproducing a suspicion |
| `pair` | Tester drives the **headed** browser; AI takes a snapshot when told ("note", "check this") and keeps the log | Main session | Tester-led sessions where the AI is the note-taker and oracle checker |

Autonomous mode never asks questions mid-session: anything needing a human (blocked action,
unclear oracle, login) is **skipped and logged** for the tester.

## 3. Charters (`3-execution/charters.md`, template `templates/charter.md`)

Generated by `exploratory-tester` (task `plan-charters`) — no browser needed. One charter per
high risk / gap cluster / journey:

```
CH-03  Explore leave request submission with boundary and invalid durations
       as ROLE-employee on test
       to discover violations of BR-012, BR-015 and J-04 step 3
Risk: R-02 (high) · Pages: PAGE-leave-new · Quirks to ignore: QK-01 · Time box: 30 min
Oracles: BR-012 (confirmed), AC-03, AC-04 · Provisional (observe only): BR-020 (observed)
Heuristics: boundaries, invalid input, double submit, back/refresh, permissions
```

Every charter names its **oracles** (and which are provisional), the **role**, the **environment**,
the **pages**, and the **quirks** to ignore. Charters for high risks are mandatory in standard and
comprehensive tiers (G4 C6).

## 4. Safety — checked before and during every session

1. **Environment.** Must be in `exploratory.environments.allowed` **and** have
   `agentsAllowed: true` in `environments.yaml`. Production: refused, no override in this stage.
2. **Origins.** Navigate only to the environment's base URL origin plus
   `exploratory.allowedOrigins` (e.g. the SSO login domain). Before every `browser_navigate`, and
   after any click that changes the URL, check the origin; if outside → go back, log, stop that path.
3. **Login without seeing credentials** (`exploratory.auth.strategy`):
   - `manual` (default): open the login page and ask the tester to log in **in the browser window**
     as the role's account; wait until the snapshot shows the signed-in state. In autonomous mode the
     orchestrator does this before handing over.
   - `storage-state`: the role has a pre-recorded session file `.auth/<env>-<role>.json` (created by
     the tester with `npx playwright codegen --save-storage=.auth/<env>-<role>.json <url>`), loaded by
     a project MCP server configured per role (`exploratory.auth.roles.<role>.mcpServer`). See
     `docs/03-credentials-and-test-accounts.md`.
   - The AI **never** types a password, reads `.env` values, or opens `.auth/*.json`.
4. **Blocked actions.** Before clicking/submitting anything whose accessible name or purpose matches
   `exploratory.guards.blockActions` (default: delete, pay, purchase, transfer, send email, send
   notification, deactivate, approve payment, purge), ask the tester (guided/pair) or **skip and log**
   (autonomous).
5. **Data.** Use data sets from `test-data.md`; for free text use a traceable prefix
   (`QA-<SES-id>-…`). Never enter real personal data. List created records in the report for cleanup.
6. **Limits.** Stop at `exploratory.guards.maxSessionMinutes` or `maxActions`; stop immediately on
   a sign of real-world side effects (emails to real addresses, payments) and report.
7. **Evidence hygiene.** No screenshots of pages showing tokens/secrets; never copy cookies or
   storage contents into files.

## 5. The exploration loop

```
repeat until charter covered, time box or action limit reached:
  1. browser_snapshot                          → where am I, what can I do (accessibility tree)
  2. choose next action from the charter + heuristics (§6), prefer untested paths
  3. safety check (§4: origin, blocked action)
  4. act: browser_click / browser_type / browser_fill_form / browser_select_option /
          browser_press_key / browser_navigate / browser_navigate_back
  5. observe: new snapshot, browser_console_messages (errors), browser_network_requests (4xx/5xx)
  6. compare with oracles (§7) → note finding if any; screenshot (browser_take_screenshot) for findings
  7. log the step in the session log (time, action, target, observation)
```

Tool names are those of `@playwright/mcp`; check the available tools at runtime (names can change
between versions). Close the browser (`browser_close`) at the end.

## 6. Heuristics (pick per charter)

| Heuristic | Try |
|---|---|
| Boundaries | min, max, max+1, zero, negative, empty, very long (≥ 1000 chars) |
| Invalid input | wrong types, bad formats, leading/trailing spaces, script-like text `<b>x</b>` |
| i18n | accents, CJK, RTL, emoji, different date/number formats |
| Interruptions | back/refresh mid-flow, double submit, two tabs on the same record, session expiry |
| Permissions | open another role's page by URL; act on another user's record; hidden-but-enabled actions |
| State | perform transitions out of order (approve a cancelled request) per `entities-states.yaml` |
| Consistency | same data shown in two places; list vs detail; totals after edits |
| Errors | messages are specific and actionable; no stack traces; recovery works |
| Accessibility basics | every input has a label; buttons have names; keyboard-only path works; focus visible |
| Responsive | `browser_resize` to 375×812 for key pages |

## 7. Oracles — what counts as a failure

| Observation | Oracle-eligible? | Becomes |
|---|---|---|
| Violates an approved AC, a `confirmed` rule, or a verified `documented` rule | yes | **defect candidate** → 3.3 draft (tester confirms) |
| Unhandled error: 5xx, uncaught console error, stack trace, crash, blank page | yes (implicit oracle) | defect candidate |
| Accessibility basics fail (no label/name, keyboard trap) | yes, if `quality-standards.md` sets an a11y target | defect candidate |
| Contradicts an `observed`/`inferred`/`disputed` fact or a pending DCP | **no** | question + discrepancy (never a defect) |
| Matches `known-quirks.md` | no | ignore (mention count only) |
| Inconsistent / surprising but no oracle | no | question or quirk candidate (DCP, review level) |
| New page, element, navigation path | – | app-map DCP (`auto` level) |
| Untested behaviour worth repeating | – | new TC suggestion (→ 2.1) / automation candidate (→ 2.3) |

## 8. Session output (`templates/session-report.md`)

`3-execution/sessions/<SES-id>/`:
- `charter.md` — copy of the charter as run (mode, role, env, build, time box)
- `session-report.md` — summary, coverage of the charter (what was/wasn't explored), timeline log,
  findings table (type, severity suggestion, oracle, evidence), created test data, skipped
  blocked actions, follow-ups
- `evidence/` — screenshots, console/network extracts (redacted), copied from the MCP output dir

Then:
1. Defect candidates → execution-analyst `draft-defects` with `traces.session` (3.3; tester confirms).
2. Questions → `questions.md`; discrepancies; DCPs (app-map pages auto-level; quirks/rules review/critical).
3. New TC / automation suggestions → listed in the report; added to 2.1/2.3 only if the tester agrees.
4. Bug re-verification → a run record for the linked TC (`mode: exploratory`, `set: retest`,
   `retestOf: DEF-xxx`) and the defect status update per 3.3 §6.
5. Audit: `SESSION-STARTED`, `SESSION-ENDED SES-xxx <findings>`.
